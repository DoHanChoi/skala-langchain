# RoleLens 기획안

## 1. 한 문장 정의

> RoleLens는 SQL이 핵심 직무가 아닌 기획자·마케터·PM이 자연어로 질문하면, 선택한 직무의 분석 관점으로 데이터를 조회하고 핵심 요약과 시각화를 제공하는 AI 데이터 도우미다.

## 2. 배경

기획자·마케터·PM은 매출, 고객, 채널, 사용자 행동 데이터를 바탕으로 의사결정하지만 SQL 작성과 DB 구조 이해는 핵심 업무가 아니다. 현재는 다음 중 하나의 비용을 지불한다.

- SQL을 직접 학습하고 작성한다.
- 데이터 분석가에게 반복적으로 조회를 요청한다.
- BI 대시보드의 제한된 필터와 차트만 사용한다.
- 결과 테이블을 다시 스프레드시트나 BI 도구에서 해석한다.

또한 같은 질문이라도 직무에 따라 관심 관점이 다르다. “최근 신규 고객 수가 어떻게 변했어?”라는 질문에서 기획자는 전체 KPI와 목표 대비, 마케터는 유입 채널과 캠페인, PM은 가입 후 활성화와 전환을 우선적으로 본다.

## 3. 문제 정의

> 데이터를 활용해야 하는 비IT 직군은 SQL과 DB 구조 학습에 시간을 쓰고, 조회 후에도 테이블을 직접 해석해야 하며, 직무에 맞는 분석 관점을 반복적으로 설정해야 한다.

## 4. 제안 솔루션

RoleLens는 사용자가 페르소나와 자연어 질문을 입력하면 다음을 수행한다.

1. 페르소나에 맞는 분석 관점 선택
2. 질문을 지표·차원·필터·기간·비교 기준으로 구조화
3. PostgreSQL 스키마를 확인하고 조회 전용 SQL 생성
4. SQL을 안전성 규칙과 DB 권한으로 검증하여 실행
5. 증감률·구성비·순위 등을 결정적 코드로 계산
6. 질문과 데이터 형태에 맞는 차트 생성
7. 직무별 핵심 요약과 근거를 Insight Card로 제공

## 5. 핵심 사용자

### 5.1 사업·서비스 기획자

- 관심: KPI, 목표 대비 실적, 전월·전분기 대비, 기여도
- 대표 질문: “이번 분기 매출이 목표 대비 어떤가?”
- 가치: 전체 성과와 격차의 주요 구성 요소를 빠르게 파악

### 5.2 CRM·그로스 마케터

- 관심: 고객 세그먼트, 유입 채널, 캠페인, 전환, 재구매
- 대표 질문: “최근 3개월 20대 고객의 카테고리별 매출은?”
- 가치: 고객·채널별 성과 차이를 캠페인 관점에서 파악

### 5.3 Product Manager

- 관심: 퍼널, 활성화, 기능 사용, 이탈, 리텐션
- 대표 질문: “신규 가입자의 7일 이내 핵심 기능 활성화율은?”
- 가치: 사용자 여정의 병목과 사용자군별 차이를 파악

## 6. LLM이 필요한 이유

- “최근”, “신규 고객”, “성과” 같은 업무 표현을 문맥과 지표 사전에 맞게 해석한다.
- 자연어 개념을 DB 테이블·컬럼·조인에 연결한다.
- 직무 관점에 따라 우선할 분석 차원과 비교 기준을 선택한다.
- 구조가 다른 조회 결과를 근거 기반의 업무 언어로 요약한다.
- 스키마·문법 오류를 구조화된 제약 안에서 수정한다.

단순 규칙 기반 시스템은 질문 표현과 DB 스키마 조합을 모두 미리 정의해야 하며 새로운 질문 유형에 유연하게 대응하기 어렵다.

## 7. 차별점

1. Text-to-SQL에서 끝나지 않고 요약·시각화·후속 질문까지 연결한다.
2. 명시적 페르소나 선택과 `RunnableBranch`로 직무별 관점을 구현한다.
3. 공통 지표 사전으로 페르소나가 바뀌어도 숫자의 의미를 일관되게 유지한다.
4. SQL·필터·기준일·사용 테이블을 공개해 결과를 검토할 수 있게 한다.
5. LLM이 임의의 Python 코드를 실행하지 않고 검증된 후처리·차트 함수만 사용한다.

## 8. 제품 형태

- 사용자 UI: Gradio Blocks 분석 워크스페이스
- 애플리케이션: Python `src` 패키지 구조
- DB: Docker Compose 기반 PostgreSQL
- 데이터: 재생성 가능한 Mock 데이터 seed
- 초기 기술 검증: Jupyter Notebook
- 제출: 소스·문서·테스트·실행 설정을 포함한 ZIP

## 9. 서비스 원칙과 한계

- RoleLens는 전문 분석가, 인과 분석, 정식 BI 보고서를 대체하지 않는다.
- 상관관계를 인과관계로 표현하지 않는다.
- 사용자가 묻지 않은 복잡한 분석을 무제한으로 확장하지 않는다.
- 지표 정의는 페르소나가 아닌 공통 의미 계층에서 관리한다.
- 모호함이 결과를 크게 바꾸면 SQL을 실행하지 않고 확인 질문을 반환한다.
- Mock 데이터에서 작동하는 학습용 MVP이며 운영 DB 연결을 보장하지 않는다.

## 10. 기대 효과

- 반복적인 데이터 조회의 대기 시간 감소
- 비IT 직군의 셀프서비스 분석 접근성 향상
- 분석가의 단순 SQL 요청 대응 비용 감소
- 직무별로 반복되는 분석 관점의 표준화
- SQL 과정과 지표 정의를 공개한 검증 가능한 분석
